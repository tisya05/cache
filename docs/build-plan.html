The platform decision

Why a PWA, not a native app

The organizers pointed at the Kuira Labs toolkit for mobile. It cannot be used on this build.

Blocker avoided

Kuira's own documentation: "Android only — no iOS, no React Native bridge, no JS interop." iOS support is roadmap, not shipped. There is a community React Native SDK (@dedanzi/midnight-mobile-sdk) that claims iOS, but it is early-stage and single-maintainer — not a foundation for a 36-hour deadline.

The Mobile track explicitly accepts "a mobile app, or mobile-first PWA." A PWA wins on every axis that matters this weekend:

  • Runs on your iPhone today — Safari → Share → Add to Home Screen. Full-screen, no browser chrome, app icon.
  • No Xcode, no Apple Developer account, no provisioning. Zero setup tax.
  • Judges can open it themselves from a link, on their own phones. Almost no other submission will offer that.
  • Seconds per iteration instead of minutes per rebuild.

Serve it over a Cloudflare tunnel so it gets real HTTPS — iOS requires that for service workers, and it hands you a public URL for the demo at the same time.

Even a flawless React Native SDK would cost time here: Xcode builds take minutes where Vite takes seconds, free provisioning certificates expire in seven days, Expo Go cannot load native modules, and judges could never open the app from a link. Every bug would be new-tool debugging against an eight-commit library with no issue history at 3am.

Already on disk

/midnight-dapp-dev:init — the official plugin scaffold — generates 32 files: Vite + React 19 + Tailwind v4 + shadcn, a wallet context, a use-contract-state hook, a proof-server status component, a wired API package, and vitest. Most valuably it includes midnight-providers.tsx, and provider assembly is the fiddliest part of any Midnight frontend. That is four to six hours we do not spend.

One adaptation: its wallet path assumes the Lace browser extension, which does not exist on iOS Safari. Lace stays on the desktop side for deploying and funding the contract; the phone uses the local-secret and relayer path instead. MeshJS @meshsdk/midnight-react is the fallback if provider assembly fights us.

System shape

Where each piece runs

The privacy claim lives or dies on this boundary, so it is worth being exact about it.

State this in the README

The proof server sees the witness. That is Midnight's normal model — you run your own proof server, which is exactly what a self-hosted deployment means. Kuira already does on-device proving on Android, so the production path is real and citable. Naming your own trust boundary earns Documentation points; hand-waving it loses them.

The contract

Four circuits, one clever trick

Everything Cache needs is built from three canonical Midnight primitives: commitments, nullifiers, and a range assertion. All three are in the plugin's reference material.

// ledger — the only things the world can see
export ledger commitments: Map<Bytes<32>, Bytes<32>>;  // user → sealed period
export ledger nullifiers:  Set<Bytes<32>>;               // one claim per period
export ledger tiers:       Map<Bytes<32>, Uint<8>>;      // achieved tier 0–4
export ledger blocks:      Map<Bytes<32>, Uint<16>>;     // city buildings earned

// 1 — register()      create identity commitment
// 2 — sealPeriod()    lock income + goal BEFORE the month runs
// 3 — proveSavings()  the whole game
// 4 — build()         spend earned blocks on the city

The savings-rate trick

Savings rate is (income − spend) / income. Division is expensive and awkward inside a ZK circuit. Rearranged, it needs only multiplication:

// tier k requires saving at least k×10 percent
assert((income - spend) * 100 >= (tier * 10) * income,
       "savings below claimed tier");

One multiply, one compare, no division, no floating point. Cheap enough that proving stays fast on a phone-sized workload — and it is the kind of specific, defensible choice a judge scoring Technology can actually point at.

The anti-cheat

sealPeriod() commits persistentCommit([income, goal], salt) at the start of the period. proveSavings() must open that same commitment. You cannot revise your income after seeing where you land on the leaderboard — the commitment simply will not open. A nullifier derived from persistentHash([secret, periodId]) stops anyone claiming the same month twice or farming duplicate accounts.

Demo weapon

Ship a Cheat Mode toggle in the demo build. Tamper with the income after sealing, hit prove, and let the contract reject it on camera. Ten seconds, no explanation needed, and it proves the cryptography is load-bearing rather than decorative.

Core loop

What actually happens each month

StepOn the phoneOn chain
SealIncome and goal entered, salt generated, commitment computedCommitment stored. Income invisible.
SpendTransactions imported and categorized locally, running total kept in IndexedDBNothing written.
ProveWitness assembled, sent to your proof server, proof returnedTier + nullifier + minted blocks.
PlayCoins spent on buildings; city re-rendersBlock count decremented.
CompareLeaderboard reads public tiers onlyAlready public — nothing new revealed.

The city is not a metaphor bolted onto a budgeting app — it is a rendering of your proof history. Every building exists because a valid zero-knowledge proof minted it. That sentence belongs in the README.

On switching to Sonnet

Sensible, but hand it a finished spec rather than an open question. Sonnet executes a well-specified screen beautifully and is far less reliable at architectural judgement calls. Keep the contract design, the trust-boundary decisions, and any "the proof is failing and I don't know why" debugging on Opus. Build screens, components, styling, and seeded data on Sonnet.
